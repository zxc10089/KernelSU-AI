# 开发文档 · KernelSU-AI（KernelSU v3.3.0 定制分支）

本文面向接手本分支的开发者：说明这支分支做了什么、代码在哪里、怎么构建、怎么验证，以及哪些契约不能碰。文档只写仓库内可查证的内容；**结论与代码不一致时以代码为准**。

阅读顺序建议：第 1 节建立全局 → 第 5 节记住红线 → 第 3 节动手构建 → 第 7、8 节了解已知问题。

## 1. 项目概览

### 1.1 组成部分

| 路径 | 形态 | 职责 |
| --- | --- | --- |
| `manager/` | Kotlin + Compose | 管理器 App。两套 UI 模式（Miuix / Material3）由 `LocalUiMode` 在运行时分发到各自的实现文件 |
| `kernel/` | C | 内核侧：supercall IOCTL、allowlist 与 app profile、sucompat、签名加冕（`check_v2_signature`） |
| `userspace/` | Rust | `ksud` 守护进程与 `ksuinit`；`userspace/ksud/src/defs.rs`（包名与版本）、`module.rs`（模块安装）、`metamodule.rs`（metamodule 守卫）是关键文件 |
| `userspace/ksud/bin/` | 预编译资产 | 补丁后的内核模块与引导载荷（aarch64），由 rust-embed 编进守护进程；x86_64 目录只有 `busybox` |
| `manager/app/src/main/assets/hiding/` | 资源包 | 随 APK 分发的隐藏模块 / 路径掩码 / 检测器 |
| `_tools/` | PowerShell | 构建、校验、资源包同步脚本（维护者工具，见 `_tools/README.md`） |

### 1.2 环境隐藏（核心特性之一）

管理器底部导航第三项「环境隐藏」提供一键安装链路，root shell 严格串行执行：

```text
Hybrid Mount(metamodule，必须最先) -> ZygiskSU -> [可选] LSPosed -> AlwaysStrong(tricky_store)
  -> HMA-OSS Zygisk -> PathMask(按运行内核分支精确命中) -> [可选] 救砖模块
安装完成后同步 HMA-OSS 预置配置；日志最后一行固定输出「需重启后生效」
```

- 入口：`manager/app/src/main/java/me/weishu/kernelsu/ui/screen/hiding/HideEnvironmentScreen.kt`（`HideEnvironmentPager`），按 `LocalUiMode` 分发到 `HideEnvironmentMiuix.kt` / `HideEnvironmentMaterial.kt`。
- 状态与流程：`ui/viewmodel/HideEnvironmentViewModel.kt`；资源读取：`data/repository/HidingPackRepository.kt`；模块冲突：`data/repository/ModuleConflictRepository*.kt`。
- 设计规格：`design/environment-hide-spec.md`。

### 1.4 与上游的差异

1. **身份收口**：`manager/gradle.properties` 定义 `KSU_PACKAGE_NAME=me.weishu.kernelsu.hide`、`KSU_VERSION_CODE=32601`、`KSU_VERSION_NAME=v3.3.0+main`；`manager/app/build.gradle.kts` 的 `getVersionCode()` / `getVersionName()` 优先读这两个 Gradle property，再回退 git 推导。

4. **内置隐藏资源包**：`manager/app/src/main/assets/hiding/`（约 130 MB）。
5. **上游 CI 归档**：`.github/workflows` → `.github/workflows.upstream`（GitHub 只执行 `.github/workflows/*.yml`）。
6. **新增内容**：`docs/`、`design/`、`_tools/`。

### 2.4 数据链

两条链，互不依赖：

```text
隐藏资源包目录 -> _tools/sync-hiding-pack.ps1 -> manager/app/src/main/assets/hiding/{manifest.json, hma_config.json, modules/, pathmask/, detectors/}
补丁后的内核模块 -> userspace/ksud/bin/aarch64/ -> rust-embed -> libksud.so -> 管理器 APK
```

设备侧：管理器以 root shell 执行 `pm install -r -t --user 0` 安装检测器 APK，并以 `execKsud module install <绝对路径>` 安装模块 → 落到 `/data/adb/modules_update/<id>` → 重启后生效为 `/data/adb/modules/<id>`；守护进程 late-load `{kmi}_kernelsu.ko`，随后由内核侧 `check_v2_signature` 完成管理器加冕。

### 2.5 身份链

加冕需要两件互相独立的事同时成立：

1. **APK 身份**：`applicationId` 与签名证书。内核侧 `kernel/manager/apk_sign.c` 先比对证书长度，再 `strcmp` 证书 SHA-256。上游期望的证书是 `0x033b`（长度）；本分支为 `0x2e8`（744），证书 SHA-256 为 `f9af24bdd3c0a4947c06eb3a3bd40c25f08e19fd1a07393ec07c6ace40e63d0e`。
2. **守护进程身份**：`userspace/ksud/src/defs.rs` 的 `DEFAULT_PACKAGE_NAME = env!("KSU_PACKAGE_NAME")`，未设置时回退 `me.weishu.kernelsu`。构建时必须传入与 `manager/gradle.properties` 相同的包名。

本分支的内核模块是用**等长字面量替换**打出来的补丁：`cmp w21, #0x33b` 改为 `cmp w21, #0x2e8`（该指令在模块二进制中只出现一次），证书 SHA-256 的十六进制字面量整体换成 `f9af24bd…`。改动集中在长度比较指令与哈希串两处，文件长度不变。这个做法意味着**无法新增 ioctl 或密钥逻辑**（新增字节会破坏等长约束），凡是需要内核新接口的方案在这支分支上都不可能实现。

由于 `libksud.so` 是预编译二进制，Gradle 构建**不会**发现包名不一致，因此有 `_tools/verify-identity.ps1`：它直接读二进制字节，核对包名、版本、证书指纹与资源包一致性。改动身份相关配置后请跑它，而不是只看构建是否成功。

## 3. 构建

### 3.1 环境前提

- Windows + Windows PowerShell 5.1 或更高。
- 工具链按「工作区根目录」布局：`<工作区>/.toolchain/{jdk-21, gradle-9.7.1, android-sdk, android-home, gradle-home, tmp}`，仓库位于 `<工作区>/<仓库目录>/`。脚本默认按此定位，可用 `-Root` 指定别处。
- Android SDK 需要 platform 37、build-tools 37.0.0、platform-tools。
- 需要自行编译 Rust 守护进程时：Rust 工具链 + `cargo-ndk` + NDK 29.0.14206865；Windows 上还需把 NDK 的 `llvm-dlltool.exe` 以 `dlltool.exe` 名称硬链接到 PATH 中（`rust-embed` 的构建脚本需要它）。
- **不要用 `gradlew.bat`**：本项目的维护环境无法通过 gradle wrapper 下载链的 TLS 校验（PKIX path building failed），构建统一走 `_tools/build-manager.ps1`；该脚本直接调用预下载的 Gradle 发行包。
- PowerShell 执行策略需放行：`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`。

### 3.2 管理器 APK

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
& .\_tools\build-manager.ps1 -Task ':app:assembleRelease' -NoDaemon
```

脚本会：定位工具链、设置 `JAVA_HOME` / `ANDROID_HOME` / `ANDROID_SDK_ROOT` / `ANDROID_USER_HOME` / `GRADLE_USER_HOME`、把 `TEMP`/`TMP` 重定向到工具链的 `tmp` 目录，并带上 `-Dorg.gradle.native=false`（默认 `%TEMP%` 被受限环境挡住时，Gradle 的 native-platform 初始化会失败）。退出时打印 `EXITCODE=`，判断成败看这一行，不要只看 Gradle 输出的末行。

构建前提：`manager/app/src/main/jniLibs/arm64-v8a/libksud.so` 必须存在（本仓库已内置），否则 `assembleRelease` 会在打包阶段失败。产物在 `manager/app/build/outputs/apk/release/`。

常用参数：`-Task`（默认 `:app:assembleDebug`）、`-WorkTree`（存在多个工作树时指定）、`-Offline`。

### 3.3 Rust 守护进程（ksud）

```powershell
& .\_tools\build-ksud.ps1 -PackageName 'me.weishu.kernelsu.hide'
```

- `-PackageName` 必须等于 `manager/gradle.properties` 的 `KSU_PACKAGE_NAME`：守护进程在编译期经 `env!("KSU_PACKAGE_NAME")` 烤进二进制，`build.rs` 在未设置时会给出 `cargo:warning`。包名决定了守护进程识别哪个管理器，以及 `late_load.rs` 强制停止/拉起哪个应用。
- `-Platform` 默认 31（与 `manager/build.gradle.kts` 的 `androidMinSdkVersion` 对齐）。不能用更低的值：bionic 只在 API 26 起导出 `__system_property_read_callback`（`userspace/ksud/src/utils.rs` 的 getprop 依赖它），否则会在最后链接阶段报 undefined symbol。
- 静态检查：`-Fmt` / `-Clippy` / `-Check` 三个开关，可组合，命中后会短路构建、只跑检查并以其退出码结束。clippy/check 也必须经 `cargo-ndk`，不能直接 `cargo clippy`。
- `-NoVerify` 跳过收尾校验。

### 3.4 资源包同步

```powershell
& .\_tools\sync-hiding-pack.ps1 -SourcePack <隐藏环境资源包目录> -IncludeDetectors
```

脚本把源目录里的模块 zip、路径掩码 zip、检测器 APK 与 HMA 预置配置收集到 `manager/app/src/main/assets/hiding/`，并重新生成 `manifest.json`。结束时打印一行统计（条目数 / 分类分布 / 总字节），可与 `manifest.json` 的 `totalBytes` 对账。

开关语义（默认值即安全值）：

| 开关 | 默认 | 说明 |
| --- | --- | --- |
| `-IncludeDetectors` | 关闭 | 检测器含闭源商业应用（例如 MT 管理器）且体积大，默认不入包 |
| `-IncludeKeybox` | 永不启用 | `keybox.xml` 含明文 EC 私钥，属于凭据，不能随仓库分发 |
| `-IncludeData` | 关闭 | `data/` 类配置数据按契约不入包 |

## 5. 关键契约与不变量

### 5.1 唯一权威 schema

`_tools/hiding_manifest.schema.json` 同时描述 `manifest.json` 的结构与管理器侧的消费语义，是这支分支的资源包契约。**不要修改它，也不要自造字段。**

### 5.2 硬约束

1. 不得重命名已有的 `hide_environment*` 字符串键（界面与断言按名字取值）。
2. 不得手工编辑 `manifest.json`，只能由 `_tools/sync-hiding-pack.ps1` 重新生成。
3. 不得把 `keybox.xml`、`target.txt` 加入资源包；`includes.keybox` 与 `includes.data` 恒为 false。
4. 不得修改或新建 `manager/app/src/test/**`、`manager/app/src/androidTest/**`。
5. 资源包的类别是闭集：`module` / `pathmask` / `detector` / `data`，没有第五类；这也是 HMA 配置以同级资产文件而不是 manifest 条目存在的原因。

### 5.3 安装顺序与集合语义

顺序由 `manifest.json` 的 `order` 决定（见 2.3 表）：metamodule 必须最先，pathmask 恰好一个，检测器永不参与一键链路（仅「快捷安装」卡片）。

集合计算：基础集合 = 可见的 `category=module` 且 id 属于 `{hybrid_mount, zygisksu, tricky_store, hma_oss_zygisk}` 的条目；按 moduleId 去重时保留最小 `order`，再按 `order` 升序排列；`zygisk_lsposed`（勾选时）、`susfs4ksu`、`Automatic_brick_rescue`（勾选时）追加进集合。

执行期：root shell 串行，绝不并发；运行中按钮禁用、状态逐步刷新；每条日志形如「第 n/m 步 · 名称 · 成功」或「失败:<原因>」，已安装的条目记为「已安装」；全部结束后**必须**追加一行「需重启后生效」，且它必须是最后一行日志。

### 5.4 metamodule 守卫（顺序为什么不能改）

`userspace/ksud/src/metamodule.rs` 的 `check_install_safety()` 在模块安装了但未重启时返回拒绝；`module.rs` 侧据此打印 `❌ Installation Blocked` 提示框并以 `Metamodule installation blocked` 结束。所有模块都先落到 `modules_update/`。

由此产生过一个死锁：`hybrid_mount` 必须最先装，而每次执行都会重装它、丢掉 `update` 标记，导致后续每一步都被守卫拒绝；管理器只能显示「失败：ksud refused to install <id>」，因为 `execKsud` 只返回布尔值，拿不到原因。

当前的缓解是流程性的，而非根因修复：安装前先查询已安装状态并跳过，同一批次内 `HYBRID_MOUNT` 装完后把 `blockedByMetamodule` 置位，让后续步骤快速失败并提示重启。修改这条链路时请保持这两个行为，否则会重新引入死锁。

### 5.5 fail-closed 归因

运行模式判定依赖内核的回答。**内核没有回答时**，运行模式必须记为 `Unknown`，不能默认成 `GkiBuiltIn`；`Unknown` 会把模式过滤整体关掉，并在页面上说明「未检测到运行模式，已显示全部内容」。不要用一个默认 false 的布尔量代替三态。

### 5.6 刷机相关

写入或回滚 `init_boot` 需要完整的沙箱权限与独占的设备锁。当前交付只处理了 A 槽，B 槽镜像未打补丁，属于已知风险（见第 8 节）。

## 6. HMA-OSS 配置同步

### 6.1 三个部件

- 模块 `hma_oss_zygisk`（order 40，作者 frknkrc44）；
- 第三方管理器应用 `org.frknkrc44.hma_oss`；
- 运行目录 `/data/misc/hide_my_applist_<随机后缀>/`（后缀随机，**不要写死**），内含 `config.json`、`filter_count.json`、`status.json`、`log/runtime.log`、`preset_cache_v2.json`、`maps_module_thread.txt`。

### 6.2 预置配置

源是资源包里的 `config.json`，由同步脚本复制为资产 `hma_config.json`（245,926 B，`configVersion` 90）。结构：`templates` 是具名模板表，只含模板「白名单」（`isWhitelist` 为 true，`appList` 2860 条）；`scope` 是「包名 → `{useWhitelist, excludeSystemApps, applyTemplates, extraAppList}`」映射，共 525 条，其中微信、QQ、TIM 三条在 `extraAppList` 里额外屏蔽了 `bin.mt.plus` 等检测类应用；`forceMountData` 为 true，`maxLogSize` 512，`detailLog` 为 false。

### 6.3 三条不变量

1. **不生成内容**：唯一来源是资源包里的 `config.json`，管理器不合成配置。
2. **不覆盖非空配置**：目标已存在非空 `config.json`（或 JSON 解析失败）都视为「已配置」，直接跳过。
3. **不假装成功**：写入后用 `wc -c` 回读字节数，必须与资产文件一致；最多重试 3 次、间隔 500 ms。

### 6.4 实现

`HideEnvironmentViewModel` 中的 `syncHmaOssConfig()` 与 `runRootCommand(shell, command): String?`：用 `ls -d /data/misc/hide_my_applist_*/` 定位目录；目录不存在 → 不适用，不写日志；`cat` 为空 → 未就绪；非空或无法解析 → 已配置；仅当配置为空时才把资产内容写入 `<dir>/config.json` 并回读。此处刻意不用 libsu 的 `ShellUtils.fastCmd`（只取首行、失败即抛）。

## 7. 已知陷阱

### 7.1 构建环境

- `gradlew.bat` 在本项目的维护环境中不可用（wrapper 下载的 TLS 校验失败），用 `_tools/build-manager.ps1` 代替。
- 受限环境会挡住默认 `%TEMP%`，Gradle 需要重定向 `TEMP`/`TMP` 并加 `-Dorg.gradle.native=false`（构建脚本已处理）。
- PowerShell 5.1 读取无 BOM 的 `.ps1` 会按 ANSI 解析：带中文注释的脚本请带 UTF-8 BOM；读 JSON 用 `Get-Content -Raw -Encoding UTF8`。
- Gradle 会把警告写到 stderr，配合 `$ErrorActionPreference = 'Stop'` 会被当成终止性错误；用退出码判断结果。

### 7.2 设备侧

- `uiautomator dump` 失败时 `adb pull` 仍可能成功，把旧 XML 当新结果；先确认 dump 成功再拉。
- `su -c` 会破坏复合命令与内层引号：把循环放到主机侧、避免内层引号，或推送脚本后执行。
- adb shell 的 `su` 可能被 SELinux 拒绝，而应用自身的 root shell 可用；两种情况要分别验证。
- 别直接 `cat` 大 JSON（`hma_config.json` 超过 240 KB），用 `head -c` / `wc -c` 截断查看。
- HMA 运行目录带随机后缀，路径不能用固定字符串匹配。

### 7.3 代码级

- 模块版本比较用相等，不要用小于：换源后版本号会重编号（例如 AlwaysStrong 从 307 变为 104），小于比较会误判为旧版本。
- 路径掩码的「已安装」判定还要比对已安装 `module.prop` 的 `updateJson` 分支（`<branch>.json`），因为六个变体共用同一个 moduleId。
- 安装用的互斥锁不可重入：持锁期间不要调用单个安装函数。
- 「需重启后生效」必须是最后一行日志，追加日志的改动要保持这个次序。
- 父容器把高度约束为 0.dp 时，用 `Modifier.requiredSize` 而不是 `size`。
- 手工改 `manifest.json` 会被下一次同步覆盖。

## 9. 上手路径

1. **读**：本文第 1、2、5 节 → `_tools/hiding_manifest.schema.json`（唯一契约）→ `design/environment-hide-spec.md`、`design/ai-console-spec.md`。

3. **构建一次**：`_tools/build-manager.ps1 -Task ':app:assembleDebug' -NoDaemon`，确认 `EXITCODE=0`。
4. **第一个改动**：建议从静态检查或纯本地逻辑入手（例如 8 节里的 schema 文案同步），改动后重新构建并回跑第 2 步。
5. **改 UI**：先 dump 基线，改完再 dump 对比 bounds，用 `measure-ui-dump.ps1` 出数字，不靠目测。
6. **改资源包**：只通过 `_tools/sync-hiding-pack.ps1`，并核对它打印的统计与 `manifest.json` 的 `totalBytes`。
